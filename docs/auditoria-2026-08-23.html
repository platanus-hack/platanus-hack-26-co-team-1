Auditoría de Aegis

El motor de detección está mejor construido que la mayoría del software que se paga. Los nueve hallazgos están casi todos en la capa de autenticación, que tiene doce horas de vida y todavía no recibió la misma disciplina que el resto.

Verificado ejecutando: suite completa, ruff (F/E9 limpio), vulture, detector de clones propio, build del front, y dos pruebas de explotación contra el backend levantado en local.

Lo primero, porque es lo que importa

Este repo no tiene el problema que se busca en una auditoría de hackatón. No hay código muerto acumulado, no hay funciones de 300 líneas, no hay copy-paste masivo, y la suite no es decorativa: 877 tests que corren en 80 segundos y que documentan la razón de cada decisión, no solo el comportamiento. El aislamiento de los tests está pensado contra accidentes reales — hay una red de contención explícita para que la suite no le escriba a la base de producción ni suba eventos falsos al panel desplegado. Eso es raro de ver.

El problema está concentrado en un solo lugar. Los últimos dos commits agregaron el circuito de altas — registro de empresa, código de enrolamiento, token de equipo — y esa capa se escribió rápido. Todos los hallazgos serios de abajo viven ahí. El motor de detección, el proxy, la política y el instalador no aportaron ninguno.

Hallazgos, por severidad

01
Crítico web/app.py:501 · _leer_politica

Cualquiera en internet puede leer el diccionario de términos internos de cualquier empresa

GET /v1/policy/<tenant> no pide token. El docstring lo justifica diciendo que la política «es la configuración que el agente OBEDECE, no datos de nadie», y eso era cierto cuando se escribió. Pero la política incluye company_terms: el diccionario término → etiqueta que la empresa carga a mano con sus nombres de proyecto, sus sistemas internos y sus archivos sensibles. El propio render.yaml la llama «la lista más sensible del sistema».

Con el nombre de la empresa alcanza. Y el nombre no es secreto: /v1/registro lo publica, y el panel lo muestra.

Ejecutado contra el backend real, sin cabecera Authorization

GET /v1/policy/acme   ->  HTTP 200
{
  "policy_version": 3,
  "company_terms": {
    "Proyecto Quimera": "codename",
    "orion-db-prod": "sistema interno",
    "margen-2027.xlsx": "financiero"
  },
  "company_terms_action": "block"
}

La ironía: es un producto anti-fuga filtrando exactamente la lista de lo que su cliente considera más secreto.

Cómo se arregla

El motivo original — «el agente no tiene con quién loguearse» — dejó de ser cierto en el commit anterior: ahora el agente sí tiene credencial, el token de equipo. Basta aceptar ese token además de la sesión y devolver 401 sin ninguno de los dos. Es la misma pieza que ya usa /v1/events, y son unas pocas líneas.

02
Alto backend/aegis_backend/enrolamiento.py:188 · emitir_equipo

El token de equipo no vence y no se puede revocar — la revocación que promete el módulo no existe

El docstring del módulo toma una decisión explícita y bien argumentada: «El token de equipo no vence… se revoca por código, no por tiempo». La primera mitad está implementada. La segunda no.

revocar() marca la fila del código y solo impide canjes futuros. El token emitido es un HMAC apátrida que no guarda ninguna referencia al código del que salió, así que leer_equipo() no tiene contra qué compararlo aunque quisiera. Un equipo ya enrolado queda afuera de todo mecanismo de baja.

Ejecutado: enrolar → revocar → reintentar

1. código creado para 'acme': AEGIS-C1KA-WT7A
2. equipo enrolado, token emitido
   ¿vale ahora?  tenant=acme
3. el admin REVOCA el código: True
   ¿se puede volver a canjear?  None      <- correcto
4. el token YA EMITIDO, después de revocar:
   tenant  ->  'acme'                    <- sigue vivo
5. cuerpo: {'tipo':'equipo','tenant':'acme','desde':1787468771}
   campos de expiración:  NINGUNO

Dos cosas lo agravan. El token se guarda en AEGIS_EVENTS_TOKEN, una variable de entorno de usuario que cualquier proceso de esa máquina puede leer — y con ella escribir eventos falsos en el panel de la empresa, que es justo el ataque que el commit anterior vino a cerrar. Y como se firma con la misma llave que las sesiones de personas, el único remedio disponible hoy es rotar esa llave: eso desloguea a todos los usuarios de todas las empresas a la vez.

Cómo se arregla

Meter en el cuerpo del token el jti del enrolamiento que lo originó, y que leer_equipo() consulte esa fila. Mantiene la decisión de no vencer — que está bien razonada — y recién ahí la revocación hace lo que el docstring dice. Guardar el token en ~/.aegis/ con ACL en vez de en el entorno es un segundo paso barato.

03
Medio web/app.py · /v1/login, /v1/enrolar, /v1/registro

No hay límite de intentos en ningún endpoint público

Los tres endpoints sin sesión aceptan intentos ilimitados. El de login es el que importa: adivinar contraseñas a máxima velocidad, sin bloqueo ni demora ni registro del intento. /v1/enrolar permite moler códigos (el espacio es grande, 32⁸, pero no hay nada que note el barrido) y /v1/registro permite ocupar nombres de empresa en masa.

Los tres ya hacen bien la parte difícil — un solo motivo de rechazo, sin filtrar si el usuario existe. Falta el contador.

Cómo se arregla

Un diccionario en memoria de intentos por IP con demora incremental cubre el 90 % del riesgo y son ~20 líneas sin dependencias, que es la restricción autoimpuesta del backend.

04
Medio cuentas.py:102 · web/app.py:762

El rol se emite, se guarda y se devuelve, pero no se verifica en ningún lado

El token lleva rol, el login lo devuelve, la tabla lo persiste. Busqué una comparación contra ese campo en todo el repo y no hay ninguna: cualquier sesión válida puede llamar cualquier endpoint de escritura, incluido el que emite códigos de enrolamiento nuevos.

Hoy no es explotable porque todas las cuentas se crean con rol="admin". Es un problema por lo que aparenta: un campo de autorización que existe invita a confiar en él. Y el default está del lado peligroso — cuenta.get("rol", "admin") — así que una fila sin ese campo se vuelve administradora.

Cómo se arregla

Una de dos, y las dos son honestas: sacar el campo hasta que haya un segundo rol, o cambiar el default a "lector" y que _con_sesion exija admin. Lo que no conviene es dejarlo como está.

05
Medio frontend/src · 5.478 líneas · 0 archivos .spec.ts

El frontend no tiene un solo test, con el runner ya instalado

Vitest y jsdom están en devDependencies, npm test está definido, y no existe ningún spec. Es la única asimetría grande del repo: 877 tests del lado Python contra cero del lado Angular, sobre código que incluye el guard de sesión, el servicio que adjunta el Authorization y la pantalla de políticas — 574 líneas de template, la más grande del proyecto.

El build en sí está sano: compila en 2 segundos, sin errores ni warnings.

Cómo se arregla

Tres specs cubren lo que duele: que sesion.service mande la cabecera, que el guard redirija sin token, y que politicas.component mapee bien la política guardada a los controles y de vuelta.

06
Bajo enrolamiento.py ↔ cuentas.py

Que un token de equipo no sirva como sesión de persona es hoy una casualidad

Los dos tipos de token comparten llave HMAC y formato de cable. Lo único que impide cruzarlos son dos chequeos de campo que no se pusieron para eso: cuentas.leer exige vence (que el token de equipo no tiene) y leer_equipo exige tipo == "equipo" (que la sesión no tiene). Funciona — hay dos tests que lo verifican — pero es frágil por construcción.

El día que alguien le agregue expiración al token de equipo, que es lo más natural del mundo y además la mitad de la corrección del hallazgo 02, ese token pasa a ser una sesión válida. Sin rol, y por el hallazgo 04, administradora.

Cómo se arregla

Un claim tipo obligatorio en ambos formatos, verificado en ambos lectores. O derivar dos llaves distintas de la del servidor con HKDF y un rótulo por uso — así el cruce ni siquiera valida la firma.

08
Bajo render.yaml · frontend/src/styles.css:1

El despliegue no es reproducible, por dos motivos distintos

El build usa npm install y no npm ci, y el propio comentario explica por qué: el package-lock.json quedó desincronizado. Además styles.css importa Inter desde Google Fonts y Angular lo resuelve en tiempo de build, así que sin red el build falla — lo comprobé sin querer, el proxy muerto de Aegis lo tumbó con ECONNREFUSED 127.0.0.1:8080.

Dos dependencias de red no fijadas en el camino que produce el panel de un producto de seguridad.

Cómo se arregla

npm install --package-lock-only para resincronizar y volver a npm ci; y bajar el woff2 de Inter a public/ con un @font-face local.

Lo que está bien y conviene no romper

  • ◆Los comentarios explican el porqué, no el qué. Casi todos citan el bug concreto o la medición que motivó la decisión. El de ocr.py justifica estar apagado por defecto con latencias medidas; el del alfabeto Crockford cuenta que un test detectó la asimetría entre S y 5. Esto es lo que hace que el repo se pueda retomar en seis meses.
  • ◆El aislamiento de la suite está pensado contra accidentes que ya pasaron. run_tests.py apaga Supabase y AEGIS_EVENTS_URL a nivel de proceso, además de tests/aislamiento.py, con el argumento correcto: el helper solo protege a quien se acuerda de usarlo.
  • ◆La revisión estática está calibrada, no copiada. Solo F y E9, porque las reglas de estilo de ruff chocan a propósito con las convenciones del repo. Y es opcional, para no romper la promesa de que el agente arranca con Python pelado. Correr ruff completo confirma que la elección fue deliberada.
  • ◆El backend no tiene una sola dependencia externa. Lo verifiqué recorriendo el AST: backend/ y web/ usan exclusivamente la biblioteca estándar, incluido el cliente de Supabase sobre urllib.
  • ◆El tenant sale del token y nunca del cuerpo, y está escrito así en mayúsculas en los dos lugares donde importa. Es la regla correcta y está aplicada de forma consistente.
  • ◆El fix del bundle de CAs de anoche sigue en pie y quedó dentro del commit 96777ce. Los 21 tests del instalador pasan.
